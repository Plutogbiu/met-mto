## 2. 迭代目标

本版本分阶段优化批量 ZIP 下载体验和后台数据看板。当前 v1.3 已上线，v1.4 代码正在继续完善，待本版本需求全部完成后统一发布。

## 3. 需求范围

### 3.1 批量 ZIP 原生流式下载

1. 批量导出任务完成后，点击下载直接触发浏览器原生下载。
2. 浏览器能够即时显示下载进度，不再等待 Axios 将完整文件读取到前端内存。
3. 服务端继续使用流式输出，不把 ZIP 整体加载到 Java 堆内存。
4. 保留 ZIP 文件 24 小时过期清理机制。
5. 单条 PDF 下载可以沿用同一套下载机制。

### 3.2 下载安全

1. 增加短时有效的一次性下载凭证，建议有效期 5 分钟。
2. 下载凭证绑定导出任务和当前用户，只能访问对应 ZIP。
3. 下载凭证使用后失效，或至少限制重复使用次数。
4. 不将长期 JWT 直接拼接到下载地址，避免出现在浏览器历史、代理日志和服务器访问日志中。
5. 继续校验批量导出权限、任务创建人和任务状态。

### 3.3 交互优化

1. 下载按钮点击后立即变为下载中状态。
2. 下载失败时给出明确提示，可重新申请下载凭证。
3. 文件已过期时提示重新生成导出任务。
4. 不改变批量导出任务生成、失败明细和 ZIP 内容结构。

## 4. 实现方案

已采用“短时下载凭证 + 原生下载地址 + 服务端流式响应”：

1. 前端请求下载凭证接口。
2. 后端校验用户权限、任务归属和任务状态，生成 5 分钟有效凭证。
3. 前端使用带凭证的临时地址创建原生下载链接。
4. 后端验证凭证后通过 `StreamingResponseBody` 输出 ZIP。
5. 凭证使用 Redis 保存一次性状态，下载时通过 Lua 脚本原子读取并删除，避免并发重复使用。

新增接口：

1. `POST /api/admin/work-orders/export-tasks/{taskId}/download-ticket`：校验批量导出权限、任务归属、任务状态及文件有效性后，生成 5 分钟一次性凭证。
2. `GET /api/admin/work-orders/export-tasks/{taskId}/download?ticket=...`：消费凭证后以 `StreamingResponseBody` 流式输出 ZIP。

本需求不新增业务数据表或数据库补丁。Redis 不可用时不允许降级为长期 JWT 下载地址。

## 5. 验收标准

1. 29.8MB 以上 ZIP 点击后可以立即进入浏览器下载状态。
2. 前端页面不再等待完整 ZIP 读取为 Blob 后才触发下载。
3. 下载过程不造成前端页面明显内存增长。
4. 无权限用户、其他用户和已过期任务无法下载文件。
5. 下载凭证过期或使用后再次访问会失败。
6. 服务端仍然以流式方式输出 ZIP，2G 服务器内存占用稳定。

## 6. 验收结果

1. 后台下载 ZIP 时，前端仅申请小型下载凭证，随后由浏览器原生下载，不再等待 Axios 接收完整 ZIP。
2. 下载凭证绑定导出任务与创建用户，有效期 5 分钟，使用一次即失效。
3. ZIP 仍从私有目录流式读取，仍按原计划保留 24 小时后清理。
4. 下载响应增加 `Cache-Control: no-store` 与 `X-Content-Type-Options: nosniff`。
